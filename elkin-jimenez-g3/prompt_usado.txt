# Bitácora de uso de GLM 5.2 (MaaS) — Reto 3 NEXUS LIVE

## Prompt 1 — Arquitectura inicial

> "Tengo el reto NEXUS LIVE: construir un motor de reservas de entradas con concurrencia segura, idempotencia, circuit breaker e interfaz, en 80 minutos. Stack: Node.js + TypeScript. ¿Qué arquitectura propones?"

**Decisión de GLM 5.2:** Propuso una arquitectura en capas: Engine (dominio) → Checkout (servicios) → API (Express) → UI. Trazabilidad en SQLite, estado en memoria. Aceptamos la propuesta.

---

## Prompt 2 — Concurrencia segura

> "¿Cómo garantizo que 100 usuarios concurrentes no reserven el mismo asiento en Node.js?"

**Propuesta de GLM 5.2:** Usar un mutex basado en cola de promesas para serializar operaciones críticas. En Node.js (single-threaded event loop), esto previene que operaciones async se entrelacen.

**Corrección del equipo:** La propuesta era correcta. Implementamos `acquireLock()` con una cola de promesas en `engine.ts`.

---

## Prompt 3 — Idempotencia

> "¿Cómo implemento Idempotency-Key con replay y conflicto?"

**GLM 5.2 propuso:** Caché en memoria: key → { payloadHash, result }. Si misma key + mismo hash → replay. Si misma key + hash distinto → IDEMPOTENCY_CONFLICT.

**Decisión del equipo:** Aceptamos. Implementado en `engine.ts` (`idempotencyCache`).

---

## Prompt 4 — Estrategia ante timeout de pagos

> "Si el proveedor de pagos hace timeout, ¿libero el HOLD o lo mantengo?"

**Propuesta de GLM 5.2:** Liberar el HOLD inmediatamente.

**Corrección del equipo (NO seguimos la primera recomendación):** Decidimos NO liberar el HOLD en caso de TIMEOUT o ERROR. Un timeout es ambiguo: el pago podría haberse procesado. Liberar el asiento permitiría que otro usuario lo compre, generando doble venta. Mantenemos el HOLD activo y el cliente puede reintentar. Solo liberamos en DECLINED (rechazo explícito).

---

## Prompt 7 — Bug encontrado con ayuda del agente

**Problema:** Al ejecutar los tests, el test de "Confirmar HOLD ya confirmado" fallaba porque el mock de pagos no era determinista.

**Solución con GLM 5.2:** Reescribimos los tests para forzar el resultado del mock sobrescribiendo `payment.authorize`, en lugar de depender del PRNG. Tests pasaron.

## Prompt 10 — Bono C: Auditoría reproducible

> "Agrega exportación de trazabilidad: línea de tiempo de HOLD, historial de asiento, verificación de consistencia y export CSV."

**GLM 5.2 generó:** Métodos `exportHoldTimeline`, `exportSeatHistory`, `reconstructSeatState`, `exportCSV` en `audit.ts`. 7 tests en `bono-c-audit.test.ts`.

**Bug encontrado:** El checkout registraba transiciones `HELD→SOLD` duplicadas (el engine ya las registraba). Esto rompía la verificación de consistencia.

**Corrección:** Cambié el log del checkout a un evento de confirmación (`SOLD→SOLD` con metadata) en lugar de duplicar la transición de estado. 46 tests pasaron.

---

## Prompt 11 — Bono D: GLM 5.2 dentro del producto

> "Implementa un módulo que use GLM 5.2 para generar explicaciones operacionales del historial de una reserva. Debe manejar timeout, respuesta vacía, error de API y formato inesperado."

**GLM 5.2 generó:** `explainer.ts` con clase `GlmExplainer` que:
- Construye un prompt a partir de las transiciones de un HOLD o asiento.
- Llama a la API de GLM (formato OpenAI-compatible) con `AbortController` para timeout.
- Parsea la respuesta manejando múltiples formatos (choices.message.content, content, response, output).
- Genera un fallback determinista cuando GLM no está disponible o falla.

**Casos límite manejados (con tests):**
- Timeout (IP inalcanzable, 500ms)
- Error HTTP 500
- Respuesta vacía (HTTP 204)
- Formato inesperado (JSON sin campos esperados)
- GLM no configurado (sin env vars)

10 tests en `bono-d-explainer.test.ts`, todos pasaron.
